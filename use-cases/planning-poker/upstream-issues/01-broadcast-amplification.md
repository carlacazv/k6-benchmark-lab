# [Performance] Reduce full `room:state` broadcast amplification in large rooms

## Summary

A controlled performance study of `planer-poker` identified a **confirmed scaling bottleneck in the current Socket.IO state-distribution model**. The application remains functionally healthy at the tested scale, but large rooms amplify `room:state` traffic close to quadratically.

Target source tested: `c501fef57a288843546ad9f8355e1a2d0af475bc`.

| Participants in one room | `room:state` deliveries | Total state bytes | Join ACK p95 | Vote ACK p95 |
|---:|---:|---:|---:|---:|
| 5 | 50 | 29.8 KiB | 2.8 ms | 1.0 ms |
| 10 | 175 | 138.1 KiB | 4.55 ms | 2.0 ms |
| 20 | 650 | 775.1 KiB | 11.05 ms | 22.05 ms |
| 40 | 2,662 | 5.07 MiB | 36.0 ms | 68.1 ms |

Growing one room from **5 to 40 participants (8× users)** produced **53.24×** more state deliveries, **174.64×** more state bytes, **3.84×** larger p95 snapshots and **68.1×** higher vote ACK p95. The fitted state-delivery curve is approximately **O(N^1.91)** and total state bytes approximately **O(N^2.48)**.

No functional failures occurred, so this is a **capacity precursor detected before an outage threshold**.

## 5W2H

### What
Reduce the number and size of full `room:state` broadcasts generated by room mutations such as join and vote.

### Why
The current model sends a complete room snapshot after state-changing operations and delivers that snapshot to every connected participant. As room size grows, both broadcast count and snapshot size grow, creating super-linear network and message-processing cost.

### Where
- `server/src/socket.js` — `broadcast(roomId)` and state-changing Socket.IO handlers
- `server/src/rooms.js` — `snapshot(room)` payload construction
- client realtime state handling — support event-specific deltas where appropriate

### When
Before claiming or targeting large-room scalability, and before materially increasing supported room sizes.

### Who
Backend/realtime owner, with frontend support for event-contract changes and QA/performance validation.

### How
1. Keep full snapshots for initial synchronization/recovery.
2. Replace frequent full snapshots with minimal delta events where possible (`participant:joined`, `participant:left`, `round:selection-status`, `round:revealed`, `story:updated`, etc.).
3. Do not broadcast vote values before reveal; send only the minimum status required by the UI.
4. Consider batching/debouncing high-frequency updates.
5. Instrument emitted payload bytes and serialization duration per broadcast.
6. Re-run the exact 5/10/20/40 single-room matrix and compare the before/after growth curve.

### How much
Estimated engineering effort: **medium**, because this changes the realtime event contract and client state handling.

Success should be measured empirically: materially lower delivery/byte growth, lower 20/40-user tail latency, and no room-state/reveal correctness regression.

## Diagnosis

**Severity:** HIGH  
**Status:** Confirmed by controlled experiment

Aggregate concurrency up to 100 sockets distributed across five-person rooms did not show meaningful degradation, while increasing participants inside one room produced strong message and latency amplification. The first optimization target should therefore be the Socket.IO state-distribution model rather than SQLite.
